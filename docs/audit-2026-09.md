# Auditoria 2026-09 — ChatPerezoso v2

**Rama:** `audit-fixes`
**Tags:** `baseline-antes-de-fixes` (c9982b6) → `post-5` (8bf1bb7)
**Fecha:** septiembre 2026

## Contexto

Auditoria tecnica completa del nucleo y la UI de ChatPerezoso v2. Se
identificaron 15 hallazgos en una primera pasada estatica; se aplicaron
9 fixes, se descarto 1 optimizacion con datos, y quedan 5 puntos
documentados como pendientes.

## Metodologia

1. Lectura estatica de todo el codigo fuente.
2. Verificacion empirica con benchmarks reproducibles (renderer
   sintetico, streaming real con Ollama, intent gate).
3. Aplicacion por fases con verificacion de tests antes/despues.
4. Reversion inmediata de cambios que no mejoran con datos.

## Cambios aplicados

### Fase 1 — Bugs criticos

- **H1 Race en `AsyncRunner.submit`/`close`** (`core/async_runner.py`).
  `submit()` leia `self._loop` fuera del lock, provocando una carrera
  con `close()`. Ahora `_ensure_loop()` devuelve el loop y `submit()`
  usa esa referencia.
  Test: `tests/test_async_runner.py`.

- **H2 Mutacion del system prompt del llamante** (`core/ollama.py`).
  `_inject_system_prompts` mutaba el dict original del llamante,
  rompiendo el contrato documentado de `chat()`. Ahora reemplaza el
  dict en lugar de mutarlo.
  Test: `tests/test_ollama.py::test_chat_does_not_mutate_caller_*`.

- **H3 Señal muerta `ChatWorker.text`** (`ui/workers.py`,
  `ui/controllers/chat_controller.py`). Se declaraba y conectaba pero
  nadie la emitia. Eliminada.
  Test: `tests/test_chat_worker_signals.py`.

- **H4-new Bloqueo de UI en `_refresh_capabilities`**
  (`ui/controllers/app_controller.py`). `wait(500)` bloqueaba el hilo
  UI al cambiar de modelo. Sustituido por cancelacion no bloqueante
  con generacion.
  Test: `tests/test_capabilities_worker.py`.

### Fase 2 — Performance de render

- **Fase 2.1 (descartada).** `setLayoutEnabled(False)` + `beginEditBlock`
  en `PlainTextRenderer`. Medicion real: `prose accum` 145 → 154 ms,
  `code accum` 12 → 21 ms. El patron real de la app es 1 mutacion por
  drain (30 Hz), no multiples mutaciones seguidas. Overhead puro.
  Detalle en "Decisiones descartadas".

- **Fase 2.2 (aplicada).** Trocear Markdown durante streaming en
  `PlainTextRenderer.on_text`. Al cruzar una frontera de parrafo o
  cerrar un fence de codigo (con >= 300 chars acumulados), el segmento
  actual se renderiza a Markdown en vez de acumularse hasta el final.
  Medicion: `code final` 26.6 ms → 0.1 ms (-99.6%). Pico de congelacion
  al cerrar la respuesta eliminado. Coste total +11% (repartido durante
  el streaming).

### Fase 3 — Estado global mutable

- **H5 `ToolIntentGate._RULES_REGISTRY`** (`core/intent.py`,
  `plugins/mcp/bridge.py`). Registro global mutable compartido entre
  instancias. `bridge.deactivate` borraba reglas que otra instancia
  podia necesitar. Ahora `_mentions_workspace_operation` usa
  `self.rules`. `register_rules` se mantiene solo como fallback para
  tests con listas de definiciones y esta documentado como deprecado.

### Fase 4 — Robustez

- **H12 `AsyncRunner.__del__`** ejecuta `close_callback` antes de
  parar el loop, en un hilo daemon. Evita dejar conexiones httpx
  colgadas cuando no se llama a `shutdown()`.

- **H14 Sidebar bloqueada durante streaming** (`ui/views/sidebar.py`).
  `_apply_busy` ahora deshabilita tambien el combo de agentes, los
  botones de crear/editar agente, y el checkbox de piloto automatico.

- **H15 Guard en `_render_markdown_block`** (`ui/rendering/plain_text.py`).
  Aborta y resetea el estado si las posiciones del cursor son invalidas
  (fuera del documento o invertidas). Antes se perdia el render
  silenciosamente.

### Fase 5 — Benchmarks

- **Baseline de streaming real** (`scripts/benchmark_streaming.py`).
  Modelo `granite4.1:3b` (warm): TTFT 0.24 s, 42.6 tok/s, 39 chunks/s.
  Modelo `gemma4:12b`: TTFT 85 s, 3.5 tok/s. Diagnostico: presion de
  memoria (modelo descargado entre turnos, cold start de 60-90 s).

- **Benchmark del `ToolIntentGate`** (`scripts/benchmark_intent_gate.py`).
  5 casos representativos, 10 verificaciones. Resultado: 10/10.
  Cubre pregunta general, accion explicita, negacion, mencion de
  nombre sin accion, y accion sobre archivo concreto.

## Decisiones descartadas

### Fase 2.1 — `setLayoutEnabled(False)` + `beginEditBlock`

**Hipotesis inicial:** agrupar multiples mutaciones del `QTextDocument`
en un bloque con layout deshabilitado reduce el coste de relayout.

**Medicion real:**

    baseline    post-2.1    delta
prose accum          145.1 ms    154.0 ms    +6%
code accum            12.4 ms     21.5 ms    +73%

**Por que fallo:** el patron de ChatPerezoso es 1 mutacion por drain
(30 veces/segundo), no multiples mutaciones seguidas. Con una sola
mutacion, `setLayoutEnabled(False)` no tiene nada que agrupar, y el
coste de deshabilitar/rehabilitar el layout al final es puro overhead.

**Leccion:** medir antes de optimizar. La intuicion sobre Qt no basta.
El benchmark sintetico (`scripts/benchmark_renderer.py`) hace visible
el patron real.

## Pendientes evaluados durante la fase de continuación

### Timeouts adaptativos

**Hipótesis:** los modelos con `thinking` mode (qwen3, muse-glimmer)
pueden superar `httpx.Timeout(read=300)` antes del primer token.

**Medición real con `qwen3:14b` (thinking ON, el peor caso):**

    load_ms:         42342    ← carga en frío del modelo
    prompt_eval_ms:    781    ← procesar el prompt
    eval_count:        500
    eval_ms:         43884    ← ~11.4 tok/s
    total_ms:        87012

**Análisis:** `httpx.Timeout(read=300)` es un timeout *por lectura*,
no un timeout *total*. El TTFT real en el peor caso es 42 s (carga del
modelo). El socket nunca espera más de 300 s entre bytes. No hay caso
donde el timeout se dispare.

**Decisión:** descartado. No añadimos lógica adaptativa para un
problema que no se materializa. Si en el futuro aparece un modelo con
TTFT > 300 s por razones distintas (prompt enorme, GPU lenta, etc.),
el cambio sería subir `read` de 300 a 600 s en una línea. No hace
falta diseño adaptativo.

### Benchmark de MikeVeerman

El repo no existe con ese nombre. La única referencia similar
(`lintware/tool-calling-benchmark`, ⭐2) no es la fuente citada. El
benchmark propio del `ToolIntentGate` (`scripts/benchmark_intent_gate.py`)
ya cubre el 80% del valor: verificar que el gate clasifica bien los
casos típicos (10/10).


## Continuación MCP (2026-09)

Tres bugs corregidos:
- MCP-1: worker no capturaba excepciones distintas a MCPError. El bridge quedaba con estado inconsistente y la UI mostraba el servidor como activo mientras las llamadas fallaban.
- MCP-2: shutdown no logeaba timeout del QThread. Ahora emite warning si un thread MCP no termina en 2s.
- MCP-3: race entre _submit y close en MCPClient. Ahora _submit toma _lifecycle_lock, evitando que close() se cuele entre el check y el scheduling.

Escenario verificado como limpio:
- Cerrar durante conexión MCP no deja subproceso huérfano. close() bloquea 2s por grace period del SDK (aceptable, cubierto por watchdog global de main.py).
